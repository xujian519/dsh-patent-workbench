> 调研日期：2026-10-07
> 调研对象：[FuRongJun-1999/dsh-memory](https://github.com/FuRongJun-1999/dsh-memory)
> 对照基线：`/Users/xujian/projects/dsh-patent-workbench`（v1.17.0，本地实读，非文档转述）
> 调研方式：远端逐文件抓取（目录树 + contents API）+ 本地源码精读（schema / repo / shared / api）

## 摘要（先给结论）

**一句话**：灵枢是「把 AI 的记忆当证据来管」的极端样本——它的全部设计都在回答同一个问题：**这条记忆凭什么可信、凭什么可回溯、凭什么可以删**。专利工作台面对的是同一个问题的法律版本。

### 三个最该拿走的

1. **`committed` 诚实字段** —— 写入返回体区分「受理了」与「落盘了」，杜绝「假装成功」。本地已经**犯过两次同类 bug**（ADR0003、v1.16.4），却始终是单点补丁，没有形成通用口径。
2. **负记忆（被拒留痕）** —— 被拒绝的草稿不丢弃，落库带原因。这是本次调研中**业务价值最高**的一条：专利领域最稀缺的知识恰恰是「什么不行」。
3. **单一真源 + 渲染 + 防漂移校验** —— 纪律/提示词不能手抄。本地 persona 已经做了 sha256 指纹，但只做了一半（有指纹、无渲染校验闭环）。

### 最该警惕的

灵枢是**一人项目**（2102 次提交中 961 次出自第一作者，其余 3 人合计 25 次），**自建基准自评**，8 周内高速迭代。它的性能数字与「100% 逐字率」来自自家题库。
**结论：借它的机制设计（可从代码读出、可自行复现），不要引用它的效果数字。**

## 二、架构全景（业务价值 → 架构定位 → 技术实现）

### 2.1 业务价值：三条不可退让的底线

灵枢的全部机制可以归到三条底线上：

1. **写进去的东西不能被悄悄改掉**（可审计）
2. **写不进去的东西要说得清为什么**（可解释）
3. **删掉的东西必须是显式删的**（可追溯）

专利工作台面临的是同样三条的**法律版本**：

1. 一条知识条目被 AI 改了，能不能查出改前是什么？→ **执业风险**
2. AI 说「已归档」，真落盘了吗？→ **信任基础**
3. 一条知识不再被召回，是「过期压制」还是「被删了」？→ **可解释性**

### 2.2 架构定位：五件套

| 部位 | 目录 | 职责 |
|---|---|---|
| 🧠 脑 | `md_cg/` | 元认知、记忆写入闸门、遗忘判定、准入读数 |
| ⚙️ 检索引擎 | `rust/` | 零依赖检索内核（RRF 融合，与 Python 侧逐位对拍） |
| 🐝 蜂群 | `swarm/` | 自维持心跳、Gossip、WAL-HMAC |
| 📜 编译器 | `compiler/` | 5 阶段确定性编译链（验证·审计） |
| ⬢ 蜂巢 | `hive/` | worker 池、原子认领、心跳、超时终止、崩溃恢复 |

> 注：五件套中只有 🧠 脑 与 ⚙️ 检索引擎对专利工作台有直接参照价值；蜂群/蜂巢是并发多智能体设施，**不建议引入**（见 §5.3）。

### 2.3 技术实现：一条写入的完整旅程

这是灵枢最值得精读的部分——**一次写入要过四道闸门**：

```
① pack 封装（本节点签名，跨节点交换时验签）
   ↓
② audit 闸门 —— policy.json 正则裁决
   ├ 命中 forbidden（11 条）→ REJECT，写入 rejected/（负记忆）
   ├ 缺 required（6 条六要素）→ REJECT，如实列出缺失项，补齐后重写即可落盘
   └ 策略不可用/形状非法 → fail-closed（policy_unavailable），不把正文塞进队列
   ↓
③ consistency 闸门 —— 与库内已有节点查冲突/冗余
   ↓
④ forgetting.assess() —— 确定性多态判定（纯规则，0.011 秒，零 LLM 黑箱）
   ├ 重要度 ≥ 0.70            → ACCEPT
   ├ 确定性内部且冗余          → DROP
   ├ 冗余 ≥ 0.85              → MERGE
   ├ 半重复且未触发保护        → DEFER（与重要度无关）
   ├ 重要度 ≥ 0.30            → ACCEPT
   ├ 新信息 ≥ 0.15            → ACCEPT
   └ 其余                     → DEFER
   ↓
⑤ 只有最终 ACCEPT 才落盘；返回体带 committed 字段
```

**关键常量**（可独立复现）：

```
DUP_MERGE         = 0.85
DUP_DROP          = 0.60
NOVELTY_MIN       = 0.15
IMPORTANCE_MIN    = 0.30
PROTECT_IMPORTANCE= 0.70
MAX_BITS          = 4.0
MAX_COMPARE       = 240
```

**判定结果语义**：`ACCEPT` 直接落盘 / `MERGE` 并入已有节点 / `DROP` 冗余丢弃 / `DEFER` 进审核队列 / `REJECT` 进负记忆。

**设计要点**：整个裁决**零 LLM 参与**——这是它「白箱」主张的技术兑现。判定快、可复现、可解释，不依赖模型版本。

## 三、值得引入的设计（按投入产出比分档）

### P0 —— 立即可做，改动小，直接堵住现存缺陷

#### P0-1 `committed` 式诚实字段

**灵枢做法**：写入返回 `{"ok": true, "committed": false, "moved_to": "review_queue"}`。
`ok=true` 只表示「受理了」，`committed=true` 才是「落盘了」。文档原话是「**绝不假装成功**」。

**专利工作台现状**：已经**犯过两次同族 bug**：
- ADR0003 `ai-progress-cannot-complete`——AI 不能标完成
- v1.16.4「建得出、确认不了」的死草稿——草稿建了，永远确认不了

两次都是**单点补丁**，没有形成通用口径。

**建议**：在 `confirmKnowledgeDraft` / `confirmTaskDraft` / 迁移提交等**所有写入口**的返回体里显式加 `committed: boolean`，客户端区分渲染「已受理（待确认）」与「已落盘」。

- **成本**：约半天
- **收益**：消灭一整类「看起来成功了」的 bug

#### P0-2 负记忆：拒绝要留痕 ★业务价值最高

**灵枢做法**：REJECT 的条目不是丢掉，而是写入 `rejected/` 层（负记忆），带原因，`cg(op=review)` 可查。

**专利工作台现状**（已核实）：

```ts
// src/db/repo/knowledge.ts:237-238
const rejection = knowledgeDraftRejection(draft.payload)
if (rejection !== null) throw new Error(rejection)
```

**抛完就没了**——既没有「这条被拒过」，也没有「为什么被拒」。

**建议**：给知识草稿加被拒状态 + 理由字段（复用已有 `task_drafts` 表加列即可，不必新表），记录：被拒时间、拒绝理由、payload 快照、**本次 payload 实际有哪些键**。

**为什么对专利业务价值极高**——专利工作里最有价值的知识往往是「**失败知识**」：

| 失败知识 | 现在去哪了 |
|---|---|
| 这个答复思路审查员不认可 | 散落在案卷里，AI 学不到 |
| 这个检索式查不到对比文件 | 散落在案卷里，AI 学不到 |
| 这份意见陈述被驳回了 | 散落在案卷里，AI 学不到 |

**「什么不行」比「什么行」更稀缺。** 而且代价极小。

#### P0-3 知识条目的版本前像 ★执业风险

**灵枢做法**：`node_id` 同一 id 即改写，但改写前先存前像，可回滚；`cg(op=protect)` 显式加保护。

**专利工作台现状**（已核实）：

```ts
// src/db/repo/knowledge.ts:167-190  updateKnowledge —— 纯 UPDATE
db.prepare(`UPDATE knowledge_entries SET kind_code = ?, title = ?, content_md = ?, ...
            WHERE id = ?`).run(...)
```

全库 grep 结果：
- **无** `version` / `history` / `revision` / `snapshot` / `audit` 表
- **无** `prev_hash` / `signature` / `hmac`
- `sha256` 仅用于三处：内容去重（`review-memory.ts:150`）、persona 指纹（`personas/library.ts:117,128`）、图片附件占位符

**即：改前内容永久丢失。**

**建议**：加一张 `knowledge_entry_revisions`（`id, entry_id, title, content_md, tags_json, revised_at, revised_by, reason`），在 `updateKnowledge` 里先插前像。一次迁移 + 一处改动。

**风险提示**：专利知识条目被 AI 或人误改后**无法回滚**，是**执业风险**而不只是体验问题。**这条我给 P0。**

> 注：本地**已有** `supersededById`（取代链）与 `validUntil`（时效压制）——说明「不静默淘汰」的方向**已经对了**，只是缺「改前留一份」这一环。这一点比调研前的预期要好。

#### P0-4 单一真源 + 渲染 + 防漂移校验

**灵枢做法**：
- 真源 = `docs/工作纪律_认知图条目_v1.1.json`（指纹 SHA256 前 16 位 `9486668b0dadac39`）
- `scripts/render_discipline.py --write` 渲染出 `CLAUDE.md` / `AGENTS.md` / `CODEBUDDY.md` / `SKILL.md` / `RULE.mdc` 多形态
- `scripts/verify_discipline.py` 判漂移，**进发布门禁（第 8 道）**
- 关键纪律：**本文件是渲染产物，不是手抄投影**；**禁止手工书写行号锚**

**为什么直接适用**：本地 `src/personas/library.ts:117,128` 已经用 sha256 做了 persona 指纹——**思路一模一样，但只做了一半**（有指纹、没有「真源 → 渲染 → 校验」闭环）。而 system prompt 注入、persona 文本、工具说明分散在多处，任何一处手改都会静默漂移。

**建议**：把 persona / 注入文本的真源收成一份 JSON，写 render + verify 脚本，挂进 `scripts/dev-verify.mjs`。

- **成本**：一天
- **收益**：「多处同源文本」这类静默漂移被机器拦住

### P1 —— 中期，需要设计但不阻塞

#### P1-1 CCG 六要素：给知识条目加「不适用条件」

**灵枢做法**：文本类归档写入**必须**含六要素——

```
功能名 / 生效条件 / 子功能 / 执行 / 验证方式 / 不适用条件
```

`required_kinds: ['text']`（收窄到文本类），缺一即 REJECT。明确的例外：`work_wip` 等过程性内容不受此约束（但 forbidden 仍生效）。

**为什么直接适用**：这个结构本质是一张**知识卡片的最小完备契约**。而专利工作台的知识条目现在只有 `title / content_md / tags`——自由文本。

**它的杀手锏是最后一个字段。「不适用条件」是负知识的载体**——正是 P0-2 说的最稀缺的那部分。专利领域的例子：

| 知识 | 不适用条件（现在没人写） |
|---|---|
| 创造性三步法 | 本申请与对比文件技术领域不同时 |
| 审查意见答复格式 | PCT 进入中国国家阶段的特殊情形 |

**建议（务必分阶段）**：

1. 第一步：知识草稿 payload 增加**可选**字段 `applicableWhen` / `notApplicableWhen`（**先不强制**）
2. 第二步：观察 AI 是否会填；填得好，再考虑对 `kind_code='经验'` 这类**收窄强制**

**风险提示**：**不要一上来就 fail-closed**。灵枢敢强制，是因为它只服务自己，且是「先有 18 条纪律、后有闸门」。专利工作台是给人类代理人用的工具，强制必填会让 AI 写不出东西、退化成写空话。**先软后硬。**

#### P1-2 一个真正的「审核队列」（而不是「待处理」）

**灵枢做法**：
- DEFER → `review_queue`，需 `can_admin` 才能 `cg(op=review, decision=accept/reject/edit/merge/noop)`
- **写入者不得自裁**
- 但经复核后 agent 可自裁；**三类例外必须转交使用者**：
  1. 重要协议真源修改
  2. 向外部发送信息数据
  3. 可能造成信息泄露 / 病毒 / 恶意操纵的动作

**专利工作台现状**：有 `task_drafts` + 「待处理」UI，但**没有「谁有权确认」的概念**；`matter_events` 的 `approver` 是**自由文本**。

**建议**：把「**写入者不得自裁**」显式化——**AI 建的草稿，不能由 AI 确认入库**。这条在专利业务里是**执业红线**（AI 不能替代理人拍板），成本几乎为零：在 `confirmKnowledgeDraft` 入口加一个 actor 检查。

#### P1-3 冲突检测（consistency）

**灵枢做法**：写入前与库内节点查冲突/冗余，三级决策。

**专利业务的特殊性**：**法条与审查指南会改版**。库内同时存在「2020 版指南」与「2023 版指南」的知识条目时，AI 召回可能给出**互相矛盾的答复思路**。

**建议**：加**离线**检查（不是写入时）——定期扫描同 tag/同 kind 的条目对，标出可能冲突的，人工裁决。成本可控，**直接降低答复错误风险**。

#### P1-4 发布面冒烟：装出来的东西真能跑吗

**灵枢做法**：第 3 道门禁 `check_publish_smoke.py`——真 `pack` → 空沙箱真装 → 从装好的目录真启动 MCP → 真发 `initialize` + `tools/list`，断言工具面 **等于** `['cg','stg']`。

**为什么需要**：灵枢自己交代了**两次同族事故**（#38、#48）：**仓库里在、包里不在** → **装机即挂**。修完之后「仍无任何机器检查能拦住同类」，这道门禁就是那个缺口的机器化收口。

**专利工作台现状**：DSH 插件，有本地构建产物（`_local-build/*.tgz` + `current.txt`）。**「装出来的插件真的能启动、工具真的注册了」有人验过吗？**

**建议**：给 `scripts/dev-verify.mjs`（ADR0006）加一条装后冒烟腿。价值不是理论上的——**同类事故已经发生过两次**。

### P2 —— 长期，或有条件才做

#### P2-1 运行时换代指纹（长驻进程持旧模块）

**灵枢做法**：`code_generation` / `disk_generation` / `stale_on_disk` / `restart_required`，基于 `md_cg/**/*.py` 的 sha256；启动闸门 fail-closed。

**为什么对 DSH 插件特别对症**：DSH 宿主是**长驻进程**，插件代码更新后宿主不一定重启——「我改了，但跑的还是旧代码」这个问题，插件开发者一定遇到过。

**建议**：极简版——启动时算一次自身代码指纹，暴露在健康检查工具里；磁盘变了但进程没重启，UI 给「需重启生效」提示。

#### P2-2 准入读数 R1–R4（给 AI 自主权设解锁条件）

**灵枢做法**：三档自治。要拿到「完全访问档」必须满足四个读数：

| 读数 | 判据 |
|---|---|
| R1 判断非退化 | 30 天内单一 verdict 占比 < 90% |
| **R2 会说「不」** | **rejected / unresolved 3 天内各 ≥ 1** |
| R3 破坏可逆且「回过」 | 30 天内 ≥ 1 次真实回滚 |
| R4 判断收敛 | 3 个子窗驳回率严格下降且最近 < 20% |

**R2 是整个设计里最聪明的一条**：**一个从不拒绝的系统不可信**。

这与专利工作台 ADR0003「AI 不能标完成」是同一种精神，只是本地是**单点规则**，没有成体系。

**建议**：不照搬四读数（本地量级不够），但借它的**形态**——给 AI 的写权限分级，并且**用「它拒绝过什么」来解锁**。如果 AI 从来没拒过任何草稿，那说明闸门是摆设。

#### P2-3 凭据/敏感信息写入闸门 ★合规硬需求

**灵枢做法**：`policy.json` 的 **11 条 forbidden 正则**：

```
私钥块 / sk- / AKIA / gh[pousr]_ / api_key KV / app_secret|client_secret KV
password|pwd|密码|口令 KV / Bearer / URL 内嵌凭据 / tk_[0-9a-f]{8,} / mdcg1.*
```

且**写入闸门与发布闸门同一口径**——policy.json 里专门记录了「此前两闸分叉」的教训（一条明文令牌因缺此模式而过了闸）。

**专利业务的相关性（直接，不是类比）**：

| 场景 | 风险 |
|---|---|
| 客户案卷含**未公开技术方案** | 绝不能进公开库 |
| 专利自媒体产出（判例精读）发布到小红书/知乎 | **发布面必须过滤客户信息** |
| 交底书含客户名称、发明人真实姓名 | 敏感信息外泄 |

**建议**：本地**已有** `openableFile.ts` 白名单（修 P0「open-file = 本机代码执行原语」）——**把同一思路扩展到内容面**：写入/发布前扫一遍 `客户名 | 案号 | 未公开技术特征` 黑名单。

**这条如果自媒体产出线在跑，优先级应提前到 P0。**

#### P2-4 用自己的真实数据建召回评测集

**灵枢做法**：`memory-bench-1000`——从真实运行 26 天的 **60189 条**里分层抽样 **1000 条**（signal 250 / noise 400 / unlabeled 350），稳定 id（SHA1 前 10 位），**100% 观测时间覆盖**，模式化脱敏（占位符 + 哨兵值），`verify_bench.py` 四道检查（隐私 PII / 凭据 KV / 熵检测 / 内容政策）。

**专利工作台现状**（已核实，比预期好）：

```ts
// src/shared/knowledgeRecall.ts:44-46
weight: 标题 0.55 / 标签 0.45 / 正文 0.25
命中判定: score > 0.33
展示相关度: relevance = score / 0.55
```

**已经有小样本标定**——注释里有一张标定表（`IDF + 0.33 | 5/12 | 12/12 | 4/4 | 全过`），说明「换尺子必须重新刻度」的纪律**已经存在**。

**所以差距不是「没有评测」，而是「评测样本太小（12 条 / 4 条量级），不足以支撑召回算法的大改」。**

**建议**：从 `knowledge_recall_log`（**已有**，schema.ts:471，`KEEP_ROWS = 2000`）抽 500–1000 条真实召回记录，人工标 100 条「该召回 / 不该召回」，扩成最小评测集。有了它，任何召回改动都能定量。

**学它诚实的部分**：`unlabeled` 是**故意留白**（原话：「既非纯信号也非纯噪声，留给评测方自行判定」）——**不要为了好看硬标**。

## 五、不建议照搬的部分（诚实边界）

这一节与上一节同等重要。

### 5.1 不要引入向量检索——至少别以「灵枢的教训」为名

灵枢**刻意避开** embedding，走「零 LLM 白箱管线 + 确定性规则 + 中文语义归一 + 抽取式回原文」。引入向量**不是「学灵枢」，而是走与灵枢相反的路**。

**我的建议**：专利工作台**也不该急着上向量**。专利领域关键词高度稳定（法条号、技术特征术语），IDF 召回够用；真正的短板不是「语义泛化」，而是**评测样本不足**（P2-4）。

**顺序应是：先扩评测集 → 再决定要不要换引擎。** 这是目标驱动的顺序，不是技术偏好。

### 5.2 不要照搬 markdown 为唯一真源

灵枢用 md 是因为它要「人类可读、可 diff、可 git」。专利工作台是 SQLite + 案卷目录**双真源**，业务侧已定。

**但借它的「原文即真源」原则**：知识条目正文如果是对源文档的改写，必须能**逐字回到源文档**。本地有 `fileLink`，但缺「可逐字回跳」的校验。**这是执业风险控制，不是洁癖。**

### 5.3 不要引入蜂群/蜂巢（swarm / hive）

worker 池、原子认领、心跳、Gossip、WAL-HMAC——为**并发多智能体**设计。专利工作台是**单人单机**业务插件，引入这套的成本远大于收益。灵枢自己也在文档里注明「只有真实负载下才稳定」。

### 5.4 不要引入巨型工具面

灵枢历史上工具面到过 **82 个**（AEIS 侧），现在**刻意收回**到默认 `['cg','stg']`，并做了「工具面渐进披露」（常驻提示只留一行职责，参数语义按需 `cg(op=help)` 取）。

**这本身是一条教训：工具面膨胀是它踩过的坑，不是它的成就。**

专利工作台当前 **16 个** `workbench_*` 工具——**已经比它克制**。将来工具变多，学它的**渐进披露**，别学它的**数量**。

### 5.5 不要模仿它的文档体量与术语密度

| 项 | 灵枢 | 本地对照 |
|---|---|---|
| 单篇文档 | `docs/eval` 下 189KB | — |
| 自举文档 | 31 轮挖掘 / 8 万字 | — |
| 单文件代码 | `mcp_server.py` **4524 行 / 305KB** | `src/client/index.tsx` 4886 行（**你正在还的债**） |
| 术语 | 「月下契约」「五环」「条件空间」「存在性跨越」 | 密集自创术语抬高门槛 |

**但要辨析**：术语体系**不是纯负资产**。它有**产品价值**——「五环」「六要素」好记、能对外讲、能形成团队共识。专利工作台若要立内部纪律，**给它起个好名字是对的**，只是别把命名当成架构。

**单文件体量**这条尤其要警惕：本地容器 4886 行已经是你正在处理的债务，灵枢的 4524 行说明**这个坑是通病，不是个例**。

### 5.6 护栏宪章：精神可取，形式不必

`guardrail-charter.md` 是一份 31 条的「对外法案」，含身份信任层级（设计者 1.0 > 协议实例 0.9 > 蜂群 0.8 > 子智能体 0.6 > 外部插件 0.3）、动作分级、响应阶梯。

**可取的两条**：

1. **动作分级按破坏性分档**
   ```
   read        : 始终允许
   write       : 常规允许，越权时受限
   execute     : 需来源信任 ≥ 子体级
   destructive : 须设计者授权 或 高信任(≥0.95) 或 显式任务上下文；三缺一即冻结
   ```
   直接可映射到 DSH 工具权限。

2. **「三类例外必须转交人类」**（重要真源修改 / 对外发送 / 可能泄露）——对专利业务直接适用。

**不必取的**：立法体例、编章节条、对外的「宪章」定位。专利工作台需要的是**几条硬规则 + 代码里的断言**，不是一份法。

## 六、风险与诚实边界（关于本调研本身）

### 6.1 来源偏差

- 灵枢的**性能数字与「100% 逐字率」来自自家基准**（`memory-bench-1000` 与 `hive-memory-bench` 同为该作者名下的仓库）
- README 引用了第三方验证报告，但**验证者与项目的独立程度未核实**
- **结论**：借它的**机制设计**（可从代码读出、可自行复现），**不要引用它的效果数字**

### 6.2 成熟度

- 项目仅 **8 周**，2102 次提交 ≈ **平均每天 37 次**——**高速迭代期**，接口与设计会变
- 96% 提交出自一人 → **bus factor = 1**
- **结论**：把它当**设计思想的来源**，不要当**依赖**。若将来接入，接入的是 MCP 协议面（稳定），不是内部模块

### 6.3 它自己承认的能力边界（这点值得学）

灵枢在多个文档里**如实标注了自己做不到什么**：

- 发布门禁第 3 道的「诚实边界」段落：明确列出「不覆盖 DSH 桥侧 / 不覆盖真实安装路径 / 不覆盖 peer 依赖解析」
- benchmark 的「已知边界」：单一项目 26 天、label 是粗标注非人工逐条、脱敏是模式化的
- 门禁链文档：明确写出「第 1、3、8、9 道**无对应 CI workflow**」

**这种「公开写清自己做不到什么」的做法本身值得学**——本地 ADR 已有这个文化，可以做得更系统。

### 6.4 本调研自身的方法边界

- 远端抓取受网络限制，`md_cg/consistency.py` 未取到（返回 0 字节，路径可能已迁移）；`consistency` 闸门的细节由 `cg(op=consistency)` 的文档面覆盖，**代码级细节未验证**
- 全部本地结论均**实读源码**（schema.ts / repo / shared / api），未采信任何二手描述
- 灵枢侧结论中标注「文档记载」的部分（如 0.011 秒耗时、100% 逐字率）**未独立复现**

## 七、落地建议（三步走）

### 第一步（本周，2–3 天）——补四个 P0

| # | 动作 | 改动面 |
|---|---|---|
| 1 | `committed` 字段进所有写入口返回体 | 返回体 + 客户端渲染 |
| 2 | 被拒草稿落库留痕 | `task_drafts` 加列 |
| 3 | `knowledge_entry_revisions` 前像表 | 一次迁移 + `updateKnowledge` |
| 4 | persona/注入文本的真源 + 渲染 + 校验 | 新脚本 + 挂 dev-verify |

**这四条互相独立、可并行，都是加字段/加表/加脚本，不动现有逻辑。**

### 第二步（两周内）——立口径

| # | 动作 | 依据 |
|---|---|---|
| 5 | 「AI 建的草稿 AI 不能确认」actor 检查 | P1-2 |
| 6 | 发布面「装后真启动」冒烟腿 | P1-4 |
| 7 | 敏感信息内容闸门（**若自媒体产出线在跑，提前到第一步**） | P2-3 |

### 第三步（一个月，需先决策）——上结构

| # | 动作 | 前置条件 |
|---|---|---|

### 唯一的判断分歧点

如果专利工作台的定位是**给代理人日常用的工具**，那么：
- **P0-2（负记忆）** 提升 AI 能力**上限**
- **P2-3（敏感信息闸门）** 守住执业**下限**

**下限优先于上限**，所以我建议**敏感信息闸门也进第一批**。

## 附：一句话总结

灵枢值得学的**不是它的架构大小**，是它的**态度**：

- 写不进去就说写不进去（`committed`）
- 拒了就说为什么拒（负记忆）
- 删了就得是显式删的（显式遗忘）
- 改了得留前像（保护历史）
- 做不到就写明做不到（诚实边界）

**专利工作台要的正是这个态度，只是对象从「AI 的记忆」换成「代理人的案卷知识」。**
