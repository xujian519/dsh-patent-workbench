## 2. P0 · 已修（批次 1，随 v1.17.0）

> 三条的共同点：都是"**判据不在真正生效的那条路径上**"，而且原始注释都写着"已校验"。

### 2.1 ✅ `open-file` 是全仓唯一的**本机代码执行原语**，而它挂在知识条目的一个普通字段上

- **现象**：`POST /api/workbench/knowledge/open-file` 只判 `stat().isFile()` 就把路径交给系统打开器
  （`open` / `cmd /c start` / `xdg-open`）。而 `.command` `.sh` `.exe` `.lnk` `.bat` **都是普通文件**，
  `fileLink` 又能由模型知识草稿、导入数据、团队记忆写入 → "点开知识里的一条文档链接"＝**执行本机任意程序**。
- **证据**（修复前）：[`src/api/openFileRoute.ts`](../../src/api/openFileRoute.ts) 的 `openLocalFile` 三个平台分支
  （`win32: cmd /c start` / `darwin: open` / 其它：`wslview`→`xdg-open`→`gio`），
  上层只有 `if (!info.isFile()) return 400`。
  ⚠️ **真正的漏洞在"第二条腿"**：客户端优先走宿主原生 `workspaces.openPath`，失败才回退这个路由 ——
  只在路由里加白名单，在"装得全"的机器上原生腿会**完全绕过**它，而"装得全"是正常机器的默认状态。
- **严重性校准**（不要夸大）：loopback + Origin + `Sec-Fetch-Site` 围栏完整（唯一实现在
  [`src/api/http.ts`](../../src/api/http.ts)），浏览器页面打不进来 → **不是远程 RCE**；
  真实风险是"本机点了一个被误导的链接就执行了程序"，属**易用性换安全**的错位。
  另外 `.app` 这类 bundle 是目录，已被 `isFile()` 挡掉，所以实际风险面是 `.command/.sh/.exe/.lnk` 这一族。
- **修复**：新增唯一判定处 [`src/shared/openableFile.ts`](../../src/shared/openableFile.ts)（**白名单**：
  文档/表格/演示/图片/音视频/压缩包/电子书/网页；不在其中 → 降级为**在文件管理器中定位**，
  `open -R` / `explorer /select,` / `xdg-open <目录>`，fail-closed）；客户端与路由**两条腿都过它**
  （顺序由 `test/clientInvariants.test.mjs` 源码扫描钉住）；两条腿抽成可注入依赖 `OpenFileDeps`，
  单测因此不会真的调用 `open`。
- **验证**：macOS 真机不注入假实现跑 reveal 腿 → `200 {"mode":"reveal","revealed":true}`，
  会 `touch MARKER` 的 `.command` **未被执行**。

### 2.2 ✅ `read-local-file` 先整读、后截断（上限形同虚设）

- **现象**：[`src/api/routes/knowledge.ts`](../../src/api/routes/knowledge.ts) 原写法是
  `await readFile(filePath,'utf8')` **之后**才比 `content.length > MAX_LOCAL_DOC_BYTES`（1 MiB）。
  `readFile` 把整个文件物化成字符串，`info.size` 读到了却从没比较。
- **影响**：2 GB 的日志会先被整体物化进**宿主进程**（1 GB 文本 ≈ 2 GB 堆）；这条路由的入参来自
  `fileLink`，多大不由我们决定。
- **附带口径 bug**：`content.length` 是**字符**数而常量名是 `MAX_LOCAL_DOC_BYTES`（**字节**），
  1 MiB 的中文文档被判成"没超限"却已整读。
- **修复**：先按 `info.size` 判；超限时从文件句柄只读前 1 MiB（内存恒为 1 MiB），
  并去掉按字节截断处半个多字节字符产生的 `�`。对外契约不变（照旧 200 + `truncated`）。
- **实测 A/B**（120 MB 文件，同一进程口径 `heapUsed` / `maxRSS`）：

  | 路径 | 峰值 RSS | 堆增量 | 返回字符数 |
  |---|---|---|---|
  | 旧（`readFile` 整读） | **167.1 MB** | 119.8 MB | 125,829,120 |
  | 新（句柄读前 1 MiB） | **42.1 MB**（= Node 基线） | 1.0 MB | 1,048,576 |

### 2.3 ✅ `workspaces/ensure` 是全仓唯一的 HTTP 写盘端点，却零校验

- **现象**：[`src/api/routes.ts`](../../src/api/routes.ts) 只判"非空字符串"就 `mkdirSync(path,{recursive:true})`。
- **影响**（三种都实测存在）：相对路径落进**服务进程的 cwd**；`~/x` 建出一个字面量名为 `~` 的目录
  （没有任何一层做 `~` 展开）；macOS 上 `D:\Code` 建出一个名叫 `D:\Code` 的单层目录
  —— 与本仓已记录过的 WSL 同源事故（[`src/shared/hostPath.ts`](../../src/shared/hostPath.ts) 头部）同一形态。
- **同形第二入口**：`/workbench` 命令用**设置里的默认 AI 工作区**拼出资料夹路径后直接 `mkdirSync`
  （[`src/index.ts`](../../src/index.ts)）—— 设置里填相对路径就同样建到 cwd。
  **修一类缺陷时要顺"谁还会做同一件事"扫一遍**，否则修完反而制造口径不一致。
- **修复**：新增唯一判据 `isAbsoluteNativePath`（认 POSIX / 盘符 / UNC；裸 `D:` 与 `~/x` 不认），
  **两个入口都过它**；只校验、不改写用户给的路径（不猜 cwd、不替它展开 `~`）。

### 3.1 ✅ 迁移安全网自己不可靠（安全网的错误是**静默**的）

- **现象与证据**（三处叠加，[`src/db/database.ts`](../../src/db/database.ts)）：
  1. **`db.exec('PRAGMA wal_checkpoint(TRUNCATE)')` 的返回值被丢弃**（原 `database.ts:82`）。
     实测：`exec` 返回 `undefined`，只有 `prepare(...).get()` 才返回 `{busy,log,checkpointed}`。
     而下一步只 `copyFileSync(dbPath, file)`（原 `database.ts:89`）**不拷 `-wal`/`-shm`** →
     busy=1（有别的连接在读）时 WAL 未截断 → **备份缺最近事务**。
  2. **`if (!hasMeta) return undefined`**（原 `database.ts:76`）与 **`if (current === 0) return undefined`**
     （原 `database.ts:78`）：业务表在、meta 行丢了 → 当成全新库 → 从迁移 1 重放 →
     `V1_DDL` 首句是无 `IF NOT EXISTS` 的 `CREATE TABLE dictionaries`
     （[`src/db/schema.ts`](../../src/db/schema.ts) 的 `V1_DDL`）→ 抛错 → ROLLBACK →
     插件 `applyDegraded`。**数据没丢**（回滚了），但用户卡死且**一个备份都没留**。
  3. 备份只挂在 `openWorkbenchDb` 上，`migrate()` 自己不备份；迁移表也没有"版本唯一且升序"断言。
- **影响**：安全网的三条腿各有一个静默失效条件，而且**恰好都在"出事的那天"才会走到**。
  当前规模下不可感，但**做错一次的代价不对称**（用户全部任务/知识/案卷都在一个 SQLite 里）。
- **✅ 实际修复**（`src/db/database.ts`）：
  1. **备份改用 `VACUUM INTO`**（`snapshotDatabase`）。它不是"更好的 copy"，而是**换掉了机制**：
     `VACUUM INTO` 读的是**单个事务的一致性快照**，与 WAL 是否截断、是否有别的连接在读**无关**，
     产出还是**自包含单文件**（`journal_mode=delete`，没有 `-wal` 陪伴）。
     旧实现的危害不再停留在推理上 —— 见下方"真实数据实测"。
  2. **回读断言替代 `existsSync`**：备份生成后**当库打开**它，读 `schema_version`，必须正好等于迁移前版本；
     打不开或版本不符都抛错并中止迁移（宁可不删表）。旧实现只判"文件在不在"，
     而 WAL 那个坑恰好就是**文件在、内容缺**。
  3. **"业务表在而版本读不到"→ 拒绝打开**（`assertFreshDatabase`）：先看 `sqlite_master` 里有没有
     `dictionaries / tasks / task_drafts / knowledge_entries / matters / task_events`；
     有就抛错（指名坏在哪、指路 `backups/`），**不重放迁移**。真·空库照常建库。
  4. **备份移进 `migrate()`**（多一个可选 `dbPath` 参数）：备份从"打开库的函数"挪到"迁移的函数"。
     理由写在代码注释里 —— 备份是**迁移的前置条件**，两者放在一起才不会出现
     "有人新开一条建库路径、忘了先备份"（本次审计能发现这个洞，正是因为它被放错了层）。
  5. **迁移表断言**（`assertMigrationTable`）：版本号**唯一**、**严格升序**、最大版本 == `SCHEMA_VERSION`。
     原来重复/乱序会被 `migration.version <= current` 静默跳过，schema 停在半截**且无任何报错**。
  6. **同秒去重**（`freeSnapshotPath`）：`VACUUM INTO` 遇到已存在的目标文件会抛
     （实测 `output file already exists`），所以同名时依次试 `-2`/`-3`…，
     否则"同一秒内第二次开库"会变成一次"打不开工作台"的假故障。
  7. **同一 bug 类的姊妹现场**（落地时 `grep -rn copyFileSync src/ scripts/` 才发现的，
     审计本身**漏了**这三处，见 §7 第 9 条）：`scripts/knowledge-supersede.mjs`、

### 3.2 ✅ 客户端常驻轮询：面板看不见的时候照样全速跑，且每 5 秒必然全量重渲染

> **状态**：**已修（批次 3）**。判据表落在新模块
> [`src/client/pollPolicy.ts`](../../src/client/pollPolicy.ts)，接线只动 `WorkbenchApp` 里那一个 effect。

- **现象**：`WorkbenchApp` 是**无条件挂载**的（开合只切 `display`，[`src/client/styles.ts`](../../src/client/styles.ts)
  注释即写明"开合只切 display，不卸载组件"），而两个定时器从不看面板开合或标签页可见性：
  [`src/client/index.tsx`](../../src/client/index.tsx) 里 `setInterval(() => void tick(), 5000)` 与
  `setInterval(refresh, 15000)`（原 `index.tsx:1078-1079`）。
  全客户端 `visibilitychange` / `document.hidden` **零命中**。
- **影响**：稳态 **36–52 请求/分钟**（面板关着、标签页在后台也一样）；且 `tick` 内多处 `setState` 每次换新对象身份
  （`JSON.parse` 出来的新数组 `Object.is` 永不相等）→ **每 5 秒必然触发一次全量重算**（§4.4 那份预算就是给这个容器定的）。
- **✅ 实际修复**：
  1. **判据表单点**（`pollPolicy.ts`，纯函数 + 18 条用例）：轻轮询（草稿 + 到期提醒）
     **可见 + 面板开 = 5 s（原速）/ 可见 + 面板关 = 15 s / 后台 = 60 s**；
     重刷新（列表 + 选中任务详情）**只在"可见 + 面板开"时每 30 s 一次，其余不周期刷新**。
  2. **"看得见的那一刻"立刻补一轮**：面板由关到开、或标签页由后台回前台 → 立刻一次轻 + 一次重。
     这比"每 15 秒盲刷一次"更准：用户看到面板的第一帧就是刚拉的，而面板关着时**一个重请求都不发**。
  3. **值比较短路**（`keepIfEqual`）：轮询/刷新里 8 处 `setState` 全部改成
     `(prev) => keepIfEqual(prev, next)`，值没变就返回原引用 → React bail out、**不渲染**。
     这就是"每 5 秒必然重渲染"的根治（不是靠降频掩盖）。
  4. **面板态读 `ACTIVE_ATTR` 而不是接 props**：它已经是"面板是否显示"的**唯一投影**
     （`decidePanel` 单点执行，`WorkbenchHeaderEntry` 也靠它同步高亮）。从 props 再引一路
     就是同一语义的第二个来源 —— 本仓头号 bug 类别。
  5. **没有做成"面板关着就停"**：草稿弹框是产品的主要通知面（`createPortal` 挂在 `document.body`，
     关着面板也要弹；v1.12.0 的"暂存"就是为这个场景加的），所以是**降档**不是停机。
- **实测证据**（2026-10-05，本机活服务 `127.0.0.1:62620`）：
  - **连续两轮真实响应逐字段比对**（间隔 6.5 s）：`bootstrap` / `tasks` / `drafts` / `reminders/due`
    **全部逐字段相同 → `keepIfEqual` 返回原引用 → 这一轮零 `setState`、零重渲染**；
    反向验证：人为改 `tasks[0].title` 或 `stats.total` → **照旧更新**（不是"永远说没变"）。
  - **单次响应的体量**（`curl` 实测）：轻轮询 `drafts` 44 B + `reminders/due` 26 B = **70 B**；
    重刷新 `bootstrap` 21,016 B + `tasks` 7,768 B + `pending-completions` 51 B ≈ **28.8 kB**
    （选中任务时再加 detail 3.9 kB + events 11.4 kB + reviews/knowledge）。
  - **请求量推算**（由判据表的用例断言，不是"感觉少了"）：面板关着 + 可见
    **52/分 → 8/分**（且重刷新从 4 次/分 → **0 次**，字节量约 **116 kB/分 → 0.3 kB/分**）；
    标签页在后台 **52/分 → 2/分**；面板开着（用户正看着）**52/分 → 30/分**，
    但其中 24 次是 70 B 的轻轮询，且**只有数据真的变了才会渲染**。
  - **变异注入**（改 `lib/` 后跑，再重建比对逐字节）：
    去掉可见性门控 / 去掉面板门控 / 重链永远按周期跑 / `keepIfEqual` 永远返回 `next` /
    `stop()` 的两重防御同时拆掉 / `kick` 里去掉"补一轮重刷新"
    → 分别让 **2 / 2 / 4 / 1 / 1 / 3** 条断言变红。**`stop()` 的 `stopped` 守卫与 `clearTimers`
    各自单独去掉都不红**（两重防御，任一层都够用）—— 这条我按实测写下来，不假装每个守卫都被覆盖。
- **顺手抓到的一个真问题（实测才发现，不是推理）**：`GET /api/workbench/bootstrap` 的响应里
  `now`（服务端时间戳）**每轮都变**，而客户端**从不消费它**（一个字段一个字段读过：
  只用 `dictionaries` / `todayPlan` / `stats` / `memoryAvailable` / `deadlineEngineAvailable`，
  `Bootstrap` 类型里也没声明 `now`）。于是 `keepIfEqual(bootstrap, next)` 会**永远判为"变了"** ——
  代码看起来在省重渲染，实际一次也省不掉，比不写更糟（下一个人会以为这里已经优化过了）。
  现在把 `now` 放进具名的 `BOOTSTRAP_VOLATILE_KEYS` 并写明"哪天要用它就先从清单里拿掉"，
  回归测试同时钉住"清单在 + 用了清单"两件事。

### 3.3 ✅ 验收确认（任务完成）不是原子操作

- **现象**：[`src/api/routes/drafts.ts`](../../src/api/routes/drafts.ts) 的 completion 分支把一次逻辑写入
  拆成 **4 个独立事务**：`completeTaskCascade`（自带 `BEGIN IMMEDIATE`，[`src/db/repo/status.ts`](../../src/db/repo/status.ts)）
  → `linkTaskSession` → `addTaskMemory` → 最后一条**裸** `UPDATE task_drafts SET status_code=...`
  （原 `src/api/routes/drafts.ts:244`；同文件 `:204` 也有一处裸 UPDATE —— 注意 `repo/drafts.ts` 是另一个文件，
  同名不同物，引用时必须带目录）。
  这是**唯一**不手写 `withDraftConfirm` 的确认分支 —— 其余四种草稿都走
  [`src/db/repo/shared.ts`](../../src/db/repo/shared.ts) `withTransaction` 的单事务（原 `src/db/repo/shared.ts:19-31`）。
- **影响**：崩在中间 → 任务已 done、草稿仍 pending、界面继续催确认，再点一次**又写一条 summary 共享记忆**
  （无幂等键）。对用户表现为"我已经验收过了，它还在让我验收"。
- **✅ 实际修复**：四步收进**一个** `withTransaction(..., { immediate: true })`；
  同一文件的 review 分支（`createTaskReview` + 回写 `reviewId` + 标 confirmed）也一并收进单事务
  （团队记忆的 `await` 留在事务**之外** —— 不能把 SQLite 事务跨 `await` 挂着）。
  **幂等键没有加**：单事务已经把"崩在中间"这个窗口消掉，而确认分支前面还有"非 pending 直接回 400"的状态守卫，
  重放路径不会重复写记忆；再加一个 `(task_id, kind, source_draft_id)` 唯一索引要动 schema（只前向），
  收益不抵风险。**留下的边界**：老版本已经产生的半截状态（任务 done + 草稿 pending）不会自动修复 ——
  用户再点一次确认仍会补上并多写一条记忆，这一点写在发布说明里。

### 3.4 ✅ 事务边界不一致 + 全仓没有 `busy_timeout`

- **现象**：`src/` 下只有 `journal_mode = WAL` 与 `foreign_keys = ON` 两条 pragma
  （原 `database.ts:141-142`），**`busy_timeout` 全仓零命中**；
  **16 处** `db.exec('BEGIN…')` 与 `withTransaction` 的嵌套守卫口径不一致；
  任务更新是整行快照 UPDATE（无乐观锁）。
- **影响**：仓库自己把"多机共用 `DSH_HOME` 是常态"写进了注释（v1.16.4 的 `DB_PATH_MISMATCH` 就是撞到过），
  而两个连接同时写就会直接 `SQLITE_BUSY` 而不是等待。当前单机规模不可感，是**天花板问题**。
- **✅ 实际修复**：
  1. **`PRAGMA busy_timeout = 5000`**（常量 `BUSY_TIMEOUT_MS`，在 `journal_mode` 之前设
     —— 切 WAL 本身也需要短暂排他锁）。
  2. **裸 `BEGIN` 全部收敛到 `withTransaction`**：`grep -rn "exec('BEGIN" src/` 现在只剩**它自己那一处**
     （`repo/shared.ts`）。原语补了两个能力，否则这次收敛会改变语义：
     - `options.immediate: true` —— 原来 4 处手写 `BEGIN IMMEDIATE`（读-改-写 JSON 列）必须保持拿写锁；
     - `tx.rollback()` —— `plans.ts` 有 8 个"先读、发现不该写就 `ROLLBACK` 返回"的分支。
       没有显式回滚口，它们只能变成"COMMIT 一个什么都没写的事务"：**当下等价，
       但下一个人在那个分支前加一句写入就会被静默提交**。
     - 嵌套时 `tx.rollback()` **响亮抛错**（单独回滚本层在 SQLite 里不存在，除非用 SAVEPOINT）——
       静默降级成"不回滚"会让调用方以为没写进去，更坏。
  3. **口径写进代码注释**：事务里有写入就用 `immediate: true`，纯读用默认值。
  4. **幂等**：`withDraftConfirm` 从"自己手写 BEGIN/COMMIT/ROLLBACK"改为调用原语（少一处重复实现）。
- **⬜ 未做**：任务更新的**乐观锁**（整行快照 UPDATE 的覆盖问题）。
  它需要先定冲突检测语义（要不要 `revision` 列 → 要动 schema），属于设计决策而不是安全网，
  不在本轮范围内。**§3.4 只解决了一半：并发不再立刻失败，但后写仍然覆盖先写。**

> 证据在 [`repro-dev-verify-posix.mjs`](../../scripts/repro/repro-dev-verify-posix.mjs)（真 `lsof`/真信号/真拉起，

  1. **POSIX 端口归属**：`lsof -nP -iTCP:<port> -sTCP:LISTEN -t` 找 pid，再 `ps -ww -p <pid> -o comm= / -o command=`

  4. **CI**：加 `node scripts/check-verify-scripts.mjs`（零依赖、只读；现役套件缺文件或未声明套件即退出码 1）。
- **实测（本机 macOS，真机）**：
  - 只读探本机**正在跑的那个实例**（62620，桌面端）：`findPortOwner` 真读到了

  - 诱饵 A（命令行是 `node /tmp/…/dsh/lib/bin.js web --port 30903`）：真 `lsof` 找到它 →
    判据放行 → 真 `SIGTERM` → **诱饵确实死了** → 真拉起 → 同端口出现新监听者 → 新实例的
    stdout **落进了日志文件**（`token=…` 可见）。被停掉的 pid 与被杀前查到的 pid 相同。
  - 诱饵 B（不像 dsh web 的 node 进程）：**硬拒绝**且诱饵**没有被误杀**。
  - `--launcher`：`sh <launcher>` **9 ms 就返回**并把实例拉起来。
  - 找不到 `bin.js`：`blocked:true` + 退出码 2，且把探测过的 4 条候选路径原样列出来。
- **`blocked` 的语义（以及**故意偏离审计建议**的一处）**：审计建议"非 Windows 判 blocked、**别让整链失败**"。
  实际做法是"**继续跑下游、但绝不报绿**"：`restart` 记 `blocked`、`blockers` 留一条、
  verdict 记 `blocked`、退出码 2 —— 下游 health/token/套件**照跑**（人工已手工重启时它们仍然有判据意义），
  所以"整链不再停在 restart"这条建议是照做的；但**不报绿**是刻意加强：
  一个必需阶段没跑成却输出退出码 0，正是本仓 AX-V07"缺一步不算通过"要防的假绿。
  与 `blocked` 相对的是**硬停**（归属判据拒绝、停不掉旧进程）：那种情况**一个套件都不许跑** ——
  否则套件会跑在**别的实例**上，也就等于跑在**别的库**上。
- **仍然没做到的边界（诚实清单）**：
  1. **CI 上仍然不跑任何浏览器套件**。本次只加了零依赖的白名单/脚本卫生关卡；
     要在 CI 上端到端跑，还需要"隔离 profile + 独立 DB"的供给流程（本机也是**人工准备**的）。
     所以 §4.2 只解决了"**本机 macOS 具备能力**"，没解决"**CI 常态覆盖**"。
  2. **没有在 macOS 上端到端跑完过整条链**：restart 之后是 health/token/套件，
     它们要一个已装盘的隔离 profile 与独立 DB（本机 `~/.dsh/profiles/web` 是**用户自己的在用 profile**，
     不是测试 profile：它的 `dsh-patent-workbench` 指向 desktop vendor 的 1.16.4 tgz）。
     本批次**没有**去改用户的 profile，也没有为了跑通就临时造一个假 profile 混过预检。
     这一段"能不能真跑完"是**本批次最大的未验证项**，下一批要先解决"隔离 profile + 独立 DB 的供给"。
  3. `ps -ww -p <pid> -o command=` 在 POSIX 上是**空格拼接**的 argv，路径里带空格时无法可靠切列 ——
     所以代码**不去解析命令行取路径**（只在命令行里做"含 dsh / 含 web / 含 --port N"的匹配），
     dsh 入口只按固定布局发现 + `DSH_VERIFY_DSH_CMD` 显式覆盖。宁可起不来，不起错的东西。
  4. `lsof` 看不到别的用户的进程（非 root）：万一端口被 root 的进程占着，`lsof` 会给出"没有监听者"，
     链会去起新实例 → 绑定失败 → health 超时。**结论仍然是红的**（不会假绿），但报的原因是"health 超时"
     而不是"端口被别人占着" —— 这条噪声没有消除。

2. **测试文件数**：子审计报 82，实测 **83** 个 `*.test.mjs`（另有 `test/fixtures/`）。

3. **模块覆盖度 36 → 38**：口径差异，见 §4.1 末的说明。**两种口径都是真的**，

4. **迁移重放的数据后果**：一度写成"数据会被破坏"。实测是**迁移抛错 → ROLLBACK → 降级**，

5. **`docs/issues/2026-10-01-mutation-probe-maintenance.md`** 已存在（探针维护）；

6. **§3.1 的"建议方向"里有一条是错的**：原文让人"抄本仓
   [`scripts/reparent-tasks.mjs`](../../scripts/reparent-tasks.mjs) 的 `source.backup(target)`"。
   落地时实测：**`node:sqlite` 的 `db.backup` 在本机 Node v22.22.3 上是 `undefined`**
   （`package.json` 的 `engines` 是 `^22.19.0 || >=24.0.0`，即本机属于**受支持配置**）。
   也就是说那条建议指向的 API 不存在，而 `reparent-tasks.mjs` 自己就在这一行崩
   —— 它是"数据库脏到 API 走不通"时才用的**救援**脚本，最需要它的时候它不在。
   现在两边统一到 `VACUUM INTO`。**教训**：引用"本仓已有的做法"之前，先把那行代码**跑一遍**；
   "仓库里有"不等于"能跑"（这条脚本此前没有测试覆盖）。
7. **§0 的 P0 计数写错**：摘要表写 **6**，而 §2 有 3 条 + §3 有 4 条 = **7**。
   两个分节各自数得对，摘要表是手写的 —— 与 §7 第 2 条同一类错误（"数量"类结论必须自己数一遍）。
8. **「同一 bug 类」的覆盖面：审计只找到了最要命的那一处，漏了三处姊妹现场。**
   审计把 `database.ts` 的迁移备份挖得很深（并实测推翻了它），但**没有把那句
   `copyFileSync` 当成一个「模式」去全仓搜一遍** —— 落地时 `grep -rn copyFileSync src/ scripts/`

   **教训**：找到一处缺陷后，第一件事是把**它的形状**（而不是它的位置）拿去全仓 grep。

## 附录 A：模块覆盖度测量（§4.1 的数字怎么来的）

零依赖，`node` 直接跑。思路：从 `test/*.mjs` 里对 `../lib/...` 的 import 出发做**传递闭包**，
再看 `lib/**/*.js` 里哪些模块不在闭包内，映射回 `src/` 路径。
（之所以能这么测：`tsc -p tsconfig.build.json` 为每个 src 模块产出同名 `.js`，客户端额外由 tsdown 打包成 `lib/client.js`。）

**这个口径的两条边界（批次 4 实际踩到，读数前必须先看）**：

1. **只认字面量 import**。测试里写成 ``import(`../lib/client/${path}`)`` 这种拼串，脚本看不见这条边 ——
   于是"测试真的跑了"和"数字一动不动"可以同时成立。要覆盖就写成显式清单
   （`MODULES = { 'x.js': () => import('../lib/client/x.js') }`），照着审计 §4.1 的做法。
2. **纯类型模块永远算"没被加载"**：`import type { X } from './contracts.js'` 会被 tsc **擦掉**，
   产物里没有这条运行时边。所以 `viewTypes.ts` / `contracts.ts` 这类模块的正确判据不是"被加载过"，
   而是"**零运行时导出**"（`test/clientModules.test.mjs` 里有这条断言）。
   批次 4 之后本脚本读数是 **158 / 158 可达、0 个从不被加载**（含上面这条口径修正）。

  }

  }
  return null
}

  .map((m) => resolveSpec(file, m[1])).filter((x) => x !== null)
