## 3. 逐条变更

### 3.1 扫描器（`src/matter-import/scan.ts`，新增）

- `scanWorkspaceTree(root, opts)`：广度优先扫目录树 → `candidates`（含 `relPath` / `path` / `tier` / `evidence` / 四个预填字段）+ `scanned`（`truncated` / `skippedSymlinks`）+ `tiers` 计数。
- **分档只看目录自己的名字与直接包含的文件名**：high = 目录名含申请号或含 `_matter-log.md`；mid = 有交底书/说明书/审查意见一类文件；rest = 其余。
- **申请号用严格 12 位边界** `(?<!\d)20\d{10}(?!\d)`：实测 `20260108151427`（14 位**时间戳**）会被宽松写法当成申请号。
- **不继承祖先目录的申请号**：用整条相对路径判定时，`04_审查意见/02_已答复/202311356097.5/附图/` 会因祖先含号而变成第二条候选 —— 实测真实目录树里这样多出 55 条（78 vs 23），同一个案子占多条，勾选后第二条必撞 `case_number` 的 UNIQUE 约束。
- 护栏：深度 ≤5、目录数 ≤20000（超限**置 `truncated` 明说**）、符号链接目录不下钻但**记名回报**、隐藏目录与 `node_modules`/`__pycache__` 跳过（实测这两类工具目录能凭空贡献几千个候选）。

### 3.2 落库（`src/matter-import/commit.ts`，新增）

- `commitMatterImport(db, items)`：一个事务、逐条 `try/catch`。**一条失败不拖垮整批**（983 条里撞一条就整批回滚的话用户永远导不进来），失败带下标 + 中文原因进 `failed`。
- 幂等靠**案号唯一**：同一批导两次，第二次每一条都如实报「案号已存在」并进 `failed`（比静默跳过诚实 —— 用户看得见库里已经有什么）。
- `applicationNo` 从案号**反推**（`extractApplicationNo`），不照抄界面回传值：用户可能把案号改成内部编号（如 `2026-UM-002`），那时申请号不是案号。
- 每条留痕 `extra.source = { kind: 'scan-import', relPath, importedAt }`。

### 3.3 端点（`src/api/matterImportRoute.ts`，新增）

- `POST /api/workbench/matter-import/scan`，body `{ root }`（`~` 展开成主目录；**相对路径明确拒绝**并说明「相对于谁」）。
- `POST /api/workbench/matter-import/commit`，body `{ items }`，`readJsonBody` 显式放宽到 2 MiB（缺省 256 KiB 会被约 250 KB 的载荷卡在边界上），`items` 上限 1000 条。
- 信任边界就是 **loopback 围栏**（`api/http.ts:77` 的唯一实现），与既有 `/knowledge/read-local-file` 同一姿态；**不虚构路径白名单** —— 扫描根本来就是用户自选的，白名单只会得到一个永远配不对的配置项。

### 3.4 界面（`MatterPane.tsx` / `MatterImportModal.tsx` / `useMatterImport.ts` / `matterImportApi.ts`，新增或改）

- 案卷条加「扫描导入」按钮（`data-matter-import`）。
- 三步弹窗：**填根**（预填 `~/工作`，普通输入框，不走目录选择器）→ **核对**（三档分组、其余档默认折叠、搜索框、每条可改案号/名称/案型、组级「全选/全不选」）→ **回执**（建了几条 + 失败逐条列原因）。
- 弹窗**零 `useState`**（沿用 `MatterDraftModal` 的边界）；九份状态住新 hook `useMatterImport.ts`，`index.tsx` 只加一行调用 + 一处渲染。
- 路由字面量只有 `matterImportApi.ts` 一处（由新测试的源码扫描钉住）。

### 3.6 夹带项：深度审计批次 2（数据库安全网）

同一份审计的批次 2：**只动数据库层与一处 HTTP 收尾，零 schema 变更、零迁移、零新依赖**。
三条都是"平时不可感、出事那天代价不对称"的安全网。

| # | 问题（修复前的真实行为） | 修复 |
|---|---|---|
| **B1** | 破坏性迁移前的备份是 `PRAGMA wal_checkpoint(TRUNCATE)` + `copyFileSync` **只拷主文件**。而 `db.exec(...)` 的返回值是 `undefined`（状态只有 `prepare().get()` 才拿得到），所以 **checkpoint 到底成不成功没人看**：另一个连接持有读快照时实测 `{"busy":1,"checkpointed":0}`，WAL 没截断，拷出来的备份**缺最近事务**。收尾只用 `existsSync(file)` 判"文件在不在"——而那个坑恰好就是"文件在、内容缺" | 换成 **`VACUUM INTO`** 一致快照（与 WAL 是否截断、有没有别的连接在读**无关**；产物自包含单文件、`journal_mode=delete`、顺带紧凑化），并在生成后**当库打开它**回读断言 `schema_version` 必须正好等于迁移前版本，打不开/版本不符都中止迁移。备份从 `openWorkbenchDb` **移进 `migrate()`**（备份是迁移的前置条件，放在一起才不会有人新开一条建库路径忘了它）。同一秒撞名时加 `-2`/`-3` 后缀（`VACUUM INTO` 遇到已存在目标会抛） |
| **B2** | `schema_version` 行丢了（或 `meta` 表整个没了）而业务表还在 → 被当成**全新库**，从迁移 1 重放 → `V1_DDL` 首句是不带 `IF NOT EXISTS` 的 `CREATE TABLE dictionaries` → 抛错 → ROLLBACK → 插件降级空转。**数据没丢，但用户卡死且一个备份都没留** | 新增 `assertFreshDatabase`：版本读成 0 时先看 `sqlite_master` 里有没有业务表（`dictionaries`/`tasks`/`task_drafts`/`knowledge_entries`/`matters`/`task_events`），有就**拒绝打开**并给出中文原因 + 修复路径（从 `backups/` 恢复、并删掉残留的 `-wal`/`-shm`）。真·空库不受影响。**不猜版本继续**——猜错就是拿用户的任务/知识/案卷当赌注 |
| **B3** | 迁移表本身没有不变量断言。重复版本号会被 `migration.version <= current` **静默跳过**（schema 停在半截、无任何报错）；乱序会让后面较小的版本永远不执行；加了迁移忘抬 `SCHEMA_VERSION` 同理 | 新增 `assertMigrationTable()`：版本号**唯一** + **严格升序** + 最大版本 == `SCHEMA_VERSION`，在 `migrate()` 与打开库时都跑 |
| **B4** | 确认验收（任务完成）把一件逻辑上的事拆成 **4 个独立事务**：`completeTaskCascade` → `linkTaskSession` → `addTaskMemory` → 最后一条**裸** `UPDATE task_drafts`。崩在中间 = 任务已 `done`、草稿仍 `pending`、界面继续催验收；再点一次**又写一条** summary 共享记忆 | 四步收进**一个** `withTransaction(..., { immediate: true })`；同一文件的复盘（review）确认分支也一并收进单事务（团队记忆的 `await` 留在事务**之外**）。**未加幂等键**：单事务已消掉"崩在中间"这个窗口，再加唯一索引要动 schema，收益不抵风险 |

## 4. 破坏性变更

- 无 schema 变更（**零迁移**）、无既有路由与工具签名变化、无依赖新增。
- **新增**两个端点与一个视图按钮，不改动既有行为。
- **夹带项 §3.5 有两处行为变更**（都不动数据、不动 schema）：
  1. `POST /knowledge/open-file` 对**非文档类扩展名**（`.command` `.sh` `.exe` `.lnk`… 以及
     无扩展名的脚本）不再交给系统默认程序，改为在文件管理器中定位；响应新增
     `mode` / `revealed` / `reason` 字段（老客户端忽略新字段仍然可用，不会报错）。
  2. `POST /workspaces/ensure` 对相对路径与 `~` 开头的路径返回 **400**（原来会静默建到
     服务进程的 cwd / 建出一个名叫 `~` 的目录）。客户端该调用本来就**吞异常不阻断会话**，
     所以最坏表现是"资料夹没被自动建出来"，而不是功能报错。
- **夹带项 §3.6 有三处行为变化**（同样零 schema 变更）：
  1. **并发写入改为排队等**：`PRAGMA busy_timeout = 5000`。
     此前默认 0 = 两个连接同时写就**立刻** `SQLITE_BUSY`（用户偶发"点一下保存失败、重试又好了"）。
     代价是**一次被挡住的写入最长挂 5 秒**才报错 —— 这是刻意的取舍（本机交互量级），不是回归。
  2. **`schema_version` 读不到时拒绝打开**（原来会"按版本 0"重放全部迁移 → 撞 `CREATE TABLE`
     → 回滚 → 插件降级空转 → 用户卡死且**一个备份都没留**）。现在直接给中文原因并指路
     `backups/`，**数据一行都不动**。真·空库（没有任何业务表）不受影响，照常建库。
  3. **破坏性迁移前的备份换成 `VACUUM INTO` 一致快照**：文件位置与命名口径不变
     （`backups/<库名>-<时间戳>-pre-schema<旧>to<新>.db`），但产物是**自包含单文件**
     （`journal_mode=delete`，不再有 `-wal` 伴随），同一秒内第二次备份会加 `-2` 后缀。
     **这个变化的意义是数据安全**：旧实现（checkpoint 后只拷主文件）在 WAL 未截断时产出的是
     **一份看着健康、实际缺事务的备份** —— 在用户活库上实测静默少了 3 条知识 + 3 条草稿，
     而副本 `PRAGMA integrity_check` 照样是 `ok`。**旧的备份文件仍可正常打开使用**，
     只是"从今往后新产生的备份"才是可信快照。

## 8. 已知问题

- **非 Windows 上"整链端到端"仍未验证**（§3.10）：restart 这一段在 macOS 上已具备能力并真机实测过（真 `lsof`/真 `SIGTERM`/真拉起），
  但 restart 之后的 health/token/套件需要一个**已装盘的隔离 profile + 独立 DB**，本机只有用户自己在用的 `web` profile，
  本版没有去动它、也没有造假 profile 混过预检。CI 也**仍然不跑任何浏览器套件**（只加了零依赖的白名单/脚本卫生关卡）。
  下一步是"隔离 profile + 独立 DB 的供给流程"，之后才谈"CI 上常态覆盖"。
- **`blocked` 与"硬停"的界线**（§3.10）：本机证明不了端口归属（无 `lsof` 等）或找不到 dsh 的 `bin.js` → `blocked`（下游照跑、退出码 2、**不报绿**）；
  而"归属判据拒绝"或"停不掉旧进程" → **硬停**（一个套件都不跑）。界线是：**链不认识占着端口的那个东西时，绝不允许把套件跑在它身上**。
- **`lsof` 看不到别人的进程**（非 root，Linux 上尤其）：万一端口被 root 的进程占着，`lsof` 会报"没有监听者"，
  链会去起新实例 → 绑定失败 → health 超时。**结论仍然是红的**（不假绿），但报的原因是"health 超时"而不是"端口被别人占着"。
- **`--launcher` 必须自己返回**（§3.10）：在前台把实例跑起来（`exec node …`）会让链挂到 180s 超时（现已单独报退出码 3 + 可读原因，但不返回就是错用）。
- **分档是启发式**：实测两类误判（业务分类目录会进高置信；文档转换的产物目录也可能进高置信）。所以三档都可见、都可勾选 —— 分档只影响排序与默认勾选，**不是判定**。
- **案号多数要人工补**：983 个目录里只有 26 个自带申请号。这是「只扫目录、不读台账」的必然代价。
- **`stage_code` 一律 `open`**、**`matterType` 按顶层业务目录预填**（可逐条改）：目录名与目录位置里没有可靠的办案阶段与案型信息。
- **目录扫描不读文件内容**：发明名称来自目录名，不准确时人工改。
- **界面尚未实机走查**：三个步骤的逻辑有单测与源码扫描覆盖，但按钮布局与折叠行为需要一次真实点击确认。
- **轮询的退出码级验证没做**：§3.7 的"少发请求、少重渲染"只有真机跑起来才看得见（桌面端现已跑本版，
  但**还没在界面上数过请求**）。在那之前，它的证据是"判据表的用例 + 真实响应比对 + 变异注入"，**不是"我在浏览器里数过请求"**。
- **冒烟层证明的是"代码被执行过"，不是"DOM 行为正确"**（§3.8）：`createPortal` 被就地渲染、
  最小 DOM 桩不模拟布局/事件/焦点，所以"弹窗真的挂在 `document.body` 上""键盘与焦点对不对"
  仍然只能靠实机走查。这层挡的是"props 传错 / 组件 `return null` / 整段实现被删"，不是交互回归。
- **真 lint 没做**（§3.7 的 C6 只做了零依赖那半）：`eslint-disable` 现在有台账、有理由、不许静默增长，
  但**依赖数组到底全不全，仍然没有工具在管**。真要接，最小组合是 `eslint` +
  `@typescript-eslint/parser` + `eslint-plugin-react-hooks`（只开 `react-hooks` / `no-unused-vars`）
  + CI 一步 `pnpm lint`；那要新增 devDependency 并清一轮存量告警，属于要立项的决定。
- **探针安全化拦不住 SIGKILL 本身**（§3.9）：那档只能"**下次启动时恢复**"，
  前提是有人或门禁**再跑一次**。恢复入口写在门禁开头（`recoverCrashedSessions()`）；
  手工核对用 `node scripts/repro/repro-mutation-residue.mjs`（dry-run 会报有没有没走完的账本）。
- **`spawnSync` 的超时只杀直接子进程**（§3.9 实测）：探针走不经 shell 的 `runNode()` 之后
  信号能直达，但 `pnpm build` / `pnpm test` 仍经 shell —— 它们超时会留下孤儿，
  此时靠**工作区指纹**兜底（孤儿只要写盘就会被下一次比对抓到）。**"加了超时"不等于"进程树已经死了"。**
- **工作区指纹只覆盖 `src` 与 `lib`**（§3.9）：探针写不到别处，但"别的目录被污染"这个判据看不见。
- **Excel 台账导入未实现**。将来要做时的两个要点（本次已探明，避免重蹈）：① xlsx 解析器**不能放** `src/shared/`（该目录严格禁止 `node:*`，而解压要 `node:zlib`）；② 现有的 `readZipEntry`（`src/api/routes/quick-attachments.ts`，带三层解压护栏）**不宜提取**成共享模块 —— `test/httpFence.test.mjs` 用源码扫描把 `inflateRawSync(...maxOutputLength` 钉死在那个路径上，直接 import 复用即可。
