# v1.16.4 Release Notes

> 主题：**知识草稿的字段名有了唯一口径 —— 修掉「建得出、确认不了」的死草稿**
> 上一个稳定点：`v1.16.3`
> 版本号 `1.16.4`（本文件随 `package.json` 一起改；tag / npm / GitHub Release 尚未产生，见 §7）。

## 0. 范围表（动版本号之前先填，写不出来就别发）

| 列 | 内容 |
|---|---|
| **本版主题** | 用户实测：在知识库里点「确认入库」→ `操作失败：knowledge requires content`。库里那条 pending 知识草稿有 **1668 字正文**，但它写在 `content_md` 下（调用方照着 `workbench_submit_knowledge` 的**工具参数名**填的），而入库侧只认 `contentMd`。根因是**插件自己推荐的绕行口没给 payload 字段名、也不校验**：`POST /api/workbench/drafts` 只校验外层 `kindCode`，于是任何一套“自以为对”的键名都能拿到 201，产出一份**永远确认不了**、且**弹窗正文为空**的死草稿 |
| **主线变更** | ① 新增 `src/shared/knowledgeDraftPayload.ts`：别名表（snake_case → camelCase）+ 归一化 + 准入措辞，**唯一实现**；② 建草稿路由（`POST /api/workbench/drafts`）对知识草稿当场校验：缺 `title`/`contentMd` → **400 中文原因并列出本次 payload 的键**，不再建死草稿；通过时把别名换成规范键名落库，并回报 `normalizedAliases`（静默改写字段是本仓禁止的）；③ **确认入库与草稿弹窗改走同一归一化** → 已经躺在库里的坏草稿不用改数据、不用迁移就能显示、能入库；④ 工具说明 / 界面提示补上 payload 字段名（治本：调用方不再靠猜） |
| **夹带项** | ① `test/devVerify.test.mjs` 的「本机真实状态」用例改成**按 profile 实际声明的库**核对，并补一条反向断言（声明的库与配置不一致必须拒绝）—— 它把研发用的 `verify-web.db` 当成了 fixture，任何一次“用户换库”都会假红；② `test/routes.test.mjs` 里那份空 payload 的知识草稿 fixture 改成真草稿（空 payload 正是本版要拒收的死草稿）。**为什么同版**：①② 是“本版必须让全量单测全绿”的直接前提，单独发版对用户零收益 |
| **被推迟** | ① 其他草稿类型（`task` / `review` / `completion`）**没有**做同样的建库前校验 —— `task` 草稿已在确认侧认 `reminder_offset_minutes` 别名（行为不变），要不要把“建的时候就校验”推广到全部类型另议；② 知识草稿弹窗仍不支持**编辑正文后入库**（本版只保证“看得见 + 能入库”；要改内容请先放弃草稿、走知识库的「新建/编辑」表单） |

## 3. 逐条变更

### 3.1 字段名的唯一口径（`src/shared/knowledgeDraftPayload.ts`，新增）

- `KNOWLEDGE_DRAFT_FIELD_ALIASES`：`content_md` / `kind_code` / `source_task_id` / `source_review_id` / `matter_id` / `file_link` → 规范键名（camelCase）。左列就是 `workbench_submit_knowledge` 的**参数名**。
- `normalizeKnowledgeDraftPayload`（读侧）：规范键优先；规范键为空串（“等于没写”）时回落到别名；**把命中的别名回报出来**。
- `canonicalizeKnowledgeDraftPayload`（写侧）：只换字段名，**历史键（`revision` / `replacedTitles`）与未知键原样保留** —— 宁可留着让读侧忽略，也不静默丢件。
- `knowledgeDraftRejection`：缺标题 / 缺正文的中文原因，**建草稿与确认入库共用同一份措辞**。
- `knowledgeDraftUnknownKeys`：只用于提示（不拒收）。

### 3.2 建草稿时就挡住死草稿（`src/api/routes/drafts.ts`）

`kindCode: "knowledge"` 走新分支：先 `knowledgeDraftRejection`（不通过 → 400），再 `canonicalizeKnowledgeDraftPayload` 落库。响应体在发生别名转换时带 `normalizedAliases: ["content_md"]`，有看不懂的键时带 `ignoredKeys`。**其他草稿类型行为不变**。

### 3.3 确认入库与弹窗渲染（`src/db/repo/knowledge.ts`、`src/client/components/KnowledgeDraftBody.tsx`）

- 两处都改走 `normalizeKnowledgeDraftPayload`：**已经躺在库里的**坏草稿因此不用改数据、不用迁移就能显示正文、就能入库。实测本机正式库（`patent-workbench.db`）里 **4 条 pending 知识草稿全部**是这种写法（`content_md`，`contentMd` 一个都没有，其中两条是真内容：1012 字 / 1668 字），装盘前它们点「确认入库」一律 400；本版靠这一条把它们全部救回（用真实库副本验证：确认成功、正文一字不少）。
- 旧的英文报错 `knowledge requires content` / `knowledge requires a non-empty title` 删除。
- 顺带接上 `matterId`：草稿里写了案卷以前会被**静默丢掉**（`confirmKnowledgeDraft` 根本不传这个字段），现在照写并做存在性校验（不存在 → 中文 400）。

### 3.4 说明文案补上字段名（`src/shared/knowledgeDraftOverwrite.ts`）

绕行建议原文只有 `{"kindCode":"knowledge","payload":{...}}`，**没给 payload 的字段名** —— 这正是本缺陷的入口。现在附上 `KNOWLEDGE_DRAFT_PAYLOAD_FIELDS_DOC`（规范键 + 别名 + “缺字段当场 400”），工具说明与工具回执都会带上它。文案与别名表的一致性由单测钉住（文案漂了就红）。

### 3.5 夹带项

- `test/devVerify.test.mjs`：那条“本机真实状态”用例原先硬编码 `verify-web.db` 当 fixture，本机 web profile 现在指向用户自己的 `patent-workbench-web.db`，于是它假红。改成**读 profile 实际声明的库**去核对，并新增反向断言（声明成另一个库 → 必须 `DB_PATH_MISMATCH` 拒绝）。安全性**没有放宽**：三个分支（声明了 → 放行 / 不一致 → 拒绝 / 没声明 → fail-closed）都在。
- `test/routes.test.mjs`：暂存用例的知识草稿 fixture 由 `payload: {}` 改为真草稿（空 payload 会被本版的建库前校验 400 拒收）。

## 4. 破坏性变更

- 无 schema 变更、无路由增删、无工具签名变化。
- **行为变化一条**（本版要的行为）：`POST /api/workbench/drafts` 对 `kindCode: "knowledge"` 的 payload 现在会**当场 400** 拒收缺 `title`/`contentMd` 的草稿（此前返回 201 并建出一份永远确认不了的 pending 草稿）。调用方若在依赖“先建空草稿、之后再补内容”，请改为一次提交含正文的 payload。

## 5. 依赖边界

未新增依赖。仍在 DSH `0.1.5-rc.1+` 硬下界内（只动本插件内部的字段归一化与文案）。

## 6. 验收方式与证据

- 新增 `test/knowledgeDraftPayload.test.mjs`（8 条）：别名表逐条覆盖、规范键优先、非法类型取安全默认、准入措辞（含“列出本次 payload 的键”）、写侧不丢件、未知键只提示、**文案 ↔ 别名表一致性**、**接线（确认入库 / 建草稿路由 / 弹窗三处都必须走唯一实现，且弹窗不得直读 `payload.contentMd`）**。
- `test/routes.test.mjs` 新增 1 条端到端：snake_case 建草稿 → 确认入库（正文一字不少、落库键名为规范键、回报 `normalizedAliases`）→ 直插库里的“老坏草稿”照样能入库 → 缺正文/缺标题当场 400 且原因可读 → 其他草稿类型不受影响。
- 全量单测：`pnpm test`（构建 + `node --test test/*.test.mjs`）：**1053 例 / 1051 通过 / 2 跳过 / 0 失败**。
- 真实数据（不是 fixture）：桌面正式库 `~/.dsh/workbench/patent-workbench.db` 的副本（14 任务 / schema 23）里，那条 1668 字（`content_md`）的 pending 知识草稿在装盘后**确认入库成功、正文全文一致**（bug 报告的原始现场）；本机另有 3 条同样写法的 pending 草稿，同一条路径可救。
- Web profile 实机（`dsh web`，1.16.4）：`snake_case` 建草稿 → 回报 `normalizedAliases:["content_md","kind_code"]` → 确认入库 → 关键词检索命中 → 删除自检条目（知识库回到 0 条）。

## 8. 已知问题

- 建库前校验只覆盖 `knowledge` 草稿；其他类型仍可能在确认阶段才暴露字段问题（见 §0 被推迟）。
- 本机 web profile 的 `patent-workbench` 现在指向用户的 `patent-workbench-web.db`，而研发验收链（`scripts/dev-verify.mjs`）默认声明的是 `verify-web.db` —— 直接跑会以 `DB_PATH_MISMATCH` **拒绝执行**（fail-closed，不会写坏任何库）。要跑研发链请另配 profile，或按其实际声明传 `--db-path`。
